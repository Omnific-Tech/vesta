# Vesta v0.3.0

Version 0.3.0 replaces the default Codex shell wrapper with native hook-only
integration, adds owner diagnostics and makes both providers' activity clocks
turn-agnostic. It includes merged PRs #9–#11, #13 and #14 since v0.2.6. The supported platform remains macOS
on Apple Silicon with zsh and signed-in native providers. The standalone binary
bundles its runtime; downloads and updates use HTTPS curl without GitHub login.

## Changes

- Trusted native Codex hooks spawn a detached, metadata-only watcher. Vesta no
  longer installs a `codex` shell function and does not proxy a PTY, inspect
  keystrokes, rewrite caller argv or signal the native TUI/backend. Warming uses
  the native durable queue; ordinary Codex launches retain native behavior.
- Watcher lifecycle follows the native backend. A shared daemon may outlive its
  terminal by roughly 30 minutes. Launches with any `-c` override, including
  Pulse/xswap launches, use the embedded backend inside the TUI process under
  the supported native launch policy. Vesta does not force either topology.
- Default setup migrates the exact owned legacy shell block, preserving other
  shell contents and rolling back on failure. Edited, incomplete, duplicated or
  unowned blocks fail ownership checks rather than being silently removed.
- Register every account home explicitly. A second home sharing `config.toml`
  can adopt a validated catalog already recorded as owned by Vesta. Status marks
  native registrations without a home ownership record as `inherited`; shared
  configuration alone does not make that home owned. Symlinked xswap transcripts
  are accepted only when contained in that home's resolved sessions tree.
- Idle and input usage come from the latest completed owned request of any
  origin, including system/meta prompts and Vesta keepalives. This fixes Claude
  never warming again when a meta turn followed `/compact`. Only non-Vesta
  activity renews the four-hour budget; a controls change still requires a fresh
  user prompt and reply. Subagent turns do not count.
- Concurrent Codex hooks can no longer drop events on a half-written ingress lock.
- `vesta status` labels hook mode, registered/owned/inherited homes and setup
  readiness separately from live warming eligibility. Its bounded, read-only
  live-owner scanner shows decision history, last skip, ownership and liveness,
  distinguishing native queue failures from transport failures. Older owners
  without this metadata remain identifiable as legacy.
- The compiled installer includes the full hook runtime dependency closure, so
  installed hooks do not depend on the source checkout. Persistent pause,
  resume, config and reset controls retain their v0.2.6 behavior.

## Upgrade and setup

From v0.2.1 or later, run `vesta update`. For a fresh installation or to replace
v0.2.0's older updater, download and verify the release before running `install`:

```sh
curl --disable --fail --location --proto '=https' --proto-redir '=https' https://github.com/Omnific-Tech/vesta/releases/download/v0.3.0/vesta-darwin-arm64 -o vesta-darwin-arm64
curl --disable --fail --location --proto '=https' --proto-redir '=https' https://github.com/Omnific-Tech/vesta/releases/download/v0.3.0/SHA256SUMS -o SHA256SUMS
shasum -a 256 -c SHA256SUMS
chmod +x vesta-darwin-arm64
./vesta-darwin-arm64 install
```

Use `install --warm` to opt selected providers into warming. Omitting `--warm`
preserves saved preferences and leaves new installations opted out. Update and
repair retain existing owned homes; they do not discover and adopt other accounts.
For each additional Codex home, including xswap/Pulse account homes, explicitly
register it using its actual path:

```sh
CODEX_HOME="/absolute/path/to/account-home" vesta install --provider codex
```

Review and trust only Vesta's entries in native `/hooks` in **each** Codex home.
Native hook/plugin disables and trust remain under your control; registration
does not imply trust or live eligibility. A shared-config home may show inherited
registration before explicit adoption. Do not copy credentials between homes.

After migration, open a new terminal or run `unfunction codex` in each old zsh
shell that still has Vesta's function. Sourcing `.zshrc` alone cannot remove a
function already defined in memory. Exit older wrapped sessions and relaunch
Codex to load the hook runtime. To keep one backend per session and avoid a
closed terminal's shared daemon keeping a thread warm, we recommend adding this
user-managed alias after removing the old function:

```sh
alias codex='codex --no-daemon'
```

Run `vesta status`, then submit a fresh normal prompt and wait for a completed
reply with input strictly greater than the configured threshold. Readiness alone
does not prove attachment or eligibility. See the
[Codex setup and trust guide](https://github.com/Omnific-Tech/vesta/blob/v0.3.0/docs/codex.md#setup-and-migration),
[Claude guide](https://github.com/Omnific-Tech/vesta/blob/v0.3.0/docs/claude.md) and
[setup reference](https://github.com/Omnific-Tech/vesta/blob/v0.3.0/experiments/SETUP.md).

## Compatibility and known limits

Live controls still require runtime **0.2.6 or newer**. The three
`minimumRuntimeVersion` declarations and CLI help retain that compatibility
floor: hook integration and diagnostics do not change the existing live-control
protocol. Restart owners older than 0.2.6 for controls; relaunch Codex for the new
0.3.0 integration and metadata. Older immutable assets remain available to running
sessions. Claude's native behavior, controls and warming defaults are unchanged.

Each keepalive consumes a real model turn. Cache retention and net usage savings
remain unverified. Cached input counts once; output and cumulative lifetime usage
do not qualify. Keepalives never renew the inactivity budget.

Terminal-close detection is deferred for the shared-daemon topology: closing a
terminal does not prove that its native backend ended. Warming may continue while
that backend remains alive and otherwise eligible. Queue commitment still has a
race with user activity or controls; a message committed to the native host may
finish and cannot be guaranteed retractable. Native hook metadata cannot reveal
every prompt's origin, so non-Vesta submissions cannot always be distinguished
as human versus another integration. The K-only instruction cannot enforce model
output or tool restraint. Catalog-digest changes after a runtime upgrade with
shared configuration remain untested.
